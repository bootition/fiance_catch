## 修复复核

### 自动规则入账可从具体流水追溯

此前自动规则命中写入的 `rule_applied` 事件缺少账本关联，详情页按 `ref_ledger_id` 查询时无法显示规则证据。当前实现已修复：

- `app/decisions/engine.py:145-166` 保存自动创建账本记录的 `entry_id`，并以 `ref_ledger_id=entry_id` 写入 `rule_applied` 事件。
- 同一事件继续写入 `ref_rule_id` 和 `ref_batch_id`，`detail` 包含来源流水 ID、匹配字段与模式；事件可从规则、批次和具体账本记录三条路径追溯。
- `app/routers/transactions.py:194-203` 按账本记录读取审计事件，`templates/entry_detail.html:96-118` 负责展示，因此自动入账详情能显示“规则自动入账”及匹配依据。

### HTTP 回归测试覆盖完整用户链路

`tests/test_e2e.py:843-886` 仅通过公开 HTTP 路由完成：

1. 在 `/rules` 创建并提升规则。
2. 在 `/imports/new` 上传匹配交易。
3. 找到自动创建的账本记录并验证 `rule_applied.ref_ledger_id` 与该记录一致。
4. 访问 `/transactions/{entry_id}`，断言详情展示规则自动入账和匹配模式。
5. 验证同一事件仍保留 `ref_rule_id`，规则维度追溯未回归。

该测试填补了前两轮审查识别的“服务存在但用户无法使用”及“单页有审计区但跨页面追溯断裂”缺口。

## 全面验收结果

以下阶段七交付条件已复核通过：

- 退款候选在 `/inbox` 可见，用户可经表单关联原消费；关联后待办、批次待确认数、审计事件和跨期统计一致。
- 提现必须逐笔选择允许用途；人际转账和其他中性资金流必须经人工定性。非法用途被拒绝且不写账本。
- 流水列表可打开详情，详情展示来源、批次、退款关联、人工修改和规则命中审计；编辑通过产品 UI 完成并记录 `manual_edit`。
- 批次撤销结果逐项展示保留的账本或来源、阻塞原因和可跳转入口。
- 自动规则入账可从具体流水详情追溯规则 ID、匹配字段和模式。
- 直接执行 `pytest`：**259 passed**。

## 下一阶段准入与边界

可以开始以下受控验收活动：

1. 备份 `.data/ledger.sqlite`，确认应用启动后页面均可访问。
2. 分别上传用户确认的真实支付宝 CSV 和微信 XLSX；核对导入结果中的新增、重复、跳过、退款和待确认计数。
3. 在 `/inbox` 逐笔处理退款、提现、人际/中性资金流；核对一个跨期退款是否回写原消费周期。
4. 在 `/transactions` 抽样核对来源、规则命中证据、批次归属和人工修改审计。
5. 演练一次可撤销的测试批次，确认阻塞项说明符合预期。
6. 将真实账单文件保留在项目外，不提交、不复制到文档或仓库。

下一阶段完成后，应新建用户验收/发布前运行验证报告，并依据实际结果更新 `docs/STATUS.md`。若发现账单格式差异、统计不一致或无法安全撤销，立即停止进一步导入并以新红队报告记录问题。

## 残余风险

- 运行时仍有 FastAPI/Starlette 的 Python 3.14 弃用警告；当前不影响 259 项测试通过，但升级依赖时应复测。
