# 27 Inbox 滚动性能彻底修复

**日期**：2026-08-27
**触发**：报告 26（高风险区分页）后，用户反馈**快速下滑仍闪烁**。
**性质**：报告 26 遗漏了更大的 DOM 来源——分类区 198 行 × 396 个原生 `<select>` 仍一次性渲染。本报告为其闭环，业务规则零变更。

## 1. 根因复盘（诚实披露）

报告 26 只给高风险区分了页（243 卡片 → 20），却未处理分类区。实测修复前分类区 198 组一次性渲染 396 个原生 select + 198 个 form，是快速下滑仍卡顿的主因。这是"半成品"式的修复——只解决了半个页面的渲染量。

## 2. 修复

- 数据层 `group_review_items_paged`：分页（每页 30 组）+ 按商户名模糊搜索；原 `group_review_items` 保留供 `confirm_group` 使用
- 后端：`_inbox_context` 增加 `cat_page/cat_q` 状态；新增 `GET /inbox/category?page=&q=` 局部刷新路由；POST confirm 带 `cat_page/cat_q`
- 前端：拆 `_category_table.html` 独立 partial（搜索框与表格分离，搜索输入不丢焦点）；搜索框 `hx-trigger` 300ms 防抖；分类区分页导航
- 高风险区保持 20/页（报告 26 方案不变）

## 3. 验证（真实库实测）

| 指标 | 修复前 | 修复后（第 1 页）|
|---|---|---|
| select 总数 | 573 | **60** |
| 页面 HTML | 576 KB | **70 KB** |
| 高风险卡片 | 243 | 20 |
| 分类区行 | 198 | 30 |

- **测试**：`pytest` **275 passed**（274 基线 + 新增 `test_inbox_category_pagination_and_search`），无回归
- 搜索「美团」→ 3 组命中；翻页第 2 页 → 30 组；均为局部片段非整页

## 4. 结论

**通过。** 全页 select 从 573 降至 60（降 90%），HTML 从 576KB 降至 70KB，快速下滑卡顿的 DOM 根源已消除。分类区同时获得搜索能力，处理效率提升。

## 5. 遗留（非阻塞）

- htmx 走 CDN，建议本地化（离线不可用）
- 高风险区 243 条分 13 页、分类区 198 组分 7 页，若后续仍嫌翻页多，可提高每页上限（当前 20/30）或做虚拟滚动
