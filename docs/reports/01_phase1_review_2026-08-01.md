# 重构阶段 1 审查报告

## 结论

**不通过，需修正后再进入阶段 2。**

阶段 1 的新 schema、仓储层和 pytest 基座已经完成，直接执行 `pytest` 的 112 项测试均通过。但迁移实现没有完成已批准规格要求的“备份后重置为干净新模型”。旧 schema 和旧数据继续留在正式数据库中，因此当前实现与规格及状态文档所称的“备份/重置迁移”不一致。

审查依据：`docs/decisions/01_refactor_spec.md`（`last-reviewed: 2026-08-01`）第 4、6、7.1 节。

## Findings

### P1：迁移未重置旧账，违背“旧数据不迁移”的已确认决策

**位置：** `app/migration_v2.py:241-264`、`app/db.py:281-430`

`ensure_ledger_v2()` 对有旧数据的库只执行备份和 `init_new_schema()`；后者只用 `CREATE TABLE IF NOT EXISTS` 创建八张新表，从未删除或清空 `transactions`、`import_sessions`、`import_rows`、`category_rules`，也没有移除旧账户表。`init_db()` 更会在这之前继续初始化和修复旧账本表。

这与规格“旧数据不迁移”“完成备份校验后初始化新 schema”“使用干净账本启用新模型”相冲突。运行时会同时存在两套互不关联的数据，旧页面仍读取 `transactions`，未来新页面读取 `ledger_entries`，用户无法判断哪个账本才是事实来源。

现有测试也将错误行为固定下来：`tests/test_migration_v2.py:95-98` 明确断言迁移后 `transactions` 仍有旧记录，`tests/test_ledger_schema.py:209-217` 断言旧表仍存在。这应改为验证：备份库保留旧记录，活动库不再含旧业务表或旧业务数据，且新八表完整可用。

**建议修复：** 备份并完整性校验成功后，在一个事务中删除旧业务表与旧索引/触发器，创建 v2 schema，写入 marker。旧库仅存在于时间戳备份文件。若决定为过渡保留旧 UI，则必须修改规格并明确旧/新数据的权威边界；当前用户已明确不保留旧数据，因此不推荐该方案。

### P2：备份通过文件复制执行，不能保证 SQLite 线上一致性

**位置：** `app/migration_v2.py:41-52`

`backup_db()` 使用 `shutil.copy2()` 复制正在使用的 SQLite 主文件。若数据库运行 WAL 模式或并发写入，未合并的事务可能在 `-wal` 文件中，复制主文件并运行 `PRAGMA integrity_check` 仍可能得到“结构完整但数据缺失”的备份。当前应用启动时没有显式 WAL 设置，风险较低，但这是迁移前唯一恢复点，不应依赖该假设。

**建议修复：** 使用 SQLite backup API（源连接 `backup()` 到备份连接）创建一致性快照；随后对备份执行 `integrity_check`。至少新增覆盖 WAL 模式与已提交数据的测试。
