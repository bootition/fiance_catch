# 重构阶段 2 审查报告

## 结论

**不通过，需修复导入原子性后再进入阶段 3。**

支付宝 CSV、微信 XLSX 的真实样本解析、标准化、状态筛选和同平台交易号去重均通过验证。但是，一次文件导入会通过多个独立数据库连接逐行提交，没有事务边界。写入过程任何一步失败都会留下部分来源流水和不完整批次；再次上传时这些行会被去重跳过，用户不能安全重试。

审查依据：`docs/decisions/01_refactor_spec.md`（`last-reviewed: 2026-08-01`）第 5、7.2 节。

## Findings

### P1：文件导入不是原子操作，失败后会产生不可安全重试的部分批次

**位置：** `app/importing/service.py:68-108`、`app/ledger_repo.py:20-35`、`app/ledger_repo.py:103-160`、`app/ledger_repo.py:48-70`。

`import_file()` 先通过 `create_import_batch()` 创建并提交批次，随后对每一条来源流水调用 `insert_source_transaction()`。这些仓储函数均各自打开 `with connect(...)` 连接，SQLite 会为每次调用独立提交。最后才调用 `update_batch_counts()` 写入汇总计数。

因此若中间某一行发生唯一约束以外的异常、磁盘写入失败、进程中断，或最终的计数更新失败：

- 已插入的来源流水会永久保留并关联到该批次；
- 批次可能保留默认零计数，或只留下部分计数；
- 下一次导入同一账单会把已残留行当作重复跳过；
- 用户既没有完整批次，也没有安全的重新导入路径。

账单导入是财务事实写入，必须将“创建批次、写入所有来源流水、写入批次计数”包在单个 `BEGIN IMMEDIATE` 事务中。异常必须回滚全部更改；仅正常完成时才提交。新增测试至少覆盖：

1. 在第 N 条行写入时模拟异常，断言没有 `import_batches` 或 `source_transactions` 残留。
2. 模拟计数更新异常，断言同样完整回滚。
3. 失败后重试同一文件，断言所有有效行均正常新增，而非被部分去重。

## 已通过项

- 支付宝 GB18030 CSV 能定位导出信息后的表头并标准化流水（`app/importing/alipay.py`）。
- 微信 XLSX 能定位表头并标准化日期、金额、方向和备注（`app/importing/wechat.py`）。
- 成功、跳过、退款状态分类符合阶段 2 边界；退款只以来源流水形式保存，尚未影响正式账本统计。
- 同平台 `(platform, source_txn_id)` 唯一约束与仓储去重符合规格；不进行跨平台模糊去重。
- 原文件内容未写入数据库；保存字段限于平台、订单号、时间、金额、状态、商户/商品和必要备注。
- `pytest` 135 项通过。
- 在临时 v2 数据库导入真实账单成功：
  - 支付宝：2,017 行，1,973 行来源流水新增，44 行跳过，34 行退款。
  - 微信：349 行，349 行来源流水新增，30 行退款。
  - 两批次 `row_count` 分别为 2,017 和 349，与真实账单行数一致。

## 次要测试缺口

- 没有测试空来源交易单号。schema 将 `(platform, '')` 视为唯一，若未来平台账单出现空交易号，第二条会被静默当作重复。解析器应拒绝缺少来源交易号的有效/退款行，或将其作为不可导入异常明确报告，绝不能将不同流水合并去重。
- 没有测试有效金额为零的成功交易。真实支付宝样本中有 3 条金额为零且状态为成功的来源行；应明确它们是允许保留、跳过并计数，还是进入异常队列，避免阶段 3/4 对零金额创建无意义记录。

## 阶段 2 重新通过条件

2. 对空来源交易号与零金额成功流水明确处理并补测试。

4. 更新 `docs/STATUS.md` 后重新审查。
