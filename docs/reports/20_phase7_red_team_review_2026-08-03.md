# 重构阶段七红队审查报告

## 结论

**不通过，禁止以当前工作区进行真实账单首次导入或发布。**

阶段一至六的服务层、迁移和解析安全准入仍然有效；阶段七的失败原因是交付闭环不完整：核心高风险处理能力只存在于 Python 服务层，未通过路由和页面交付给用户。对于本产品，不能由用户完成的退款关联、提现定性和人际资金定性不构成可验收功能。

审查依据：

- `docs/decisions/01_refactor_spec.md`（`status: approved`，`last-reviewed: 2026-08-01`）第 2.1、2.3、3.3、3.4、3.6、7.6、8 节。
- `docs/STATUS.md`（审查开始时最后更新于 2026-08-03）：阶段六通过后进入阶段七用户验收、真实账单首次导入和发布前运行验证。

## 审查范围与方法

审查覆盖生产挂载的 FastAPI 路由、Jinja 模板、导入/决策/退款/撤销服务、统计查询和阶段六端到端测试。重点检查规格规定的用户动作是否能够从浏览器走通，而非仅检查 Python 函数是否存在。

已执行：

```text
pytest
253 passed, 1392 warnings in 7.78s
```

全量测试通过不改变本报告结论。测试存在绕过 HTTP/UI 直接调用领域服务的情况，不能证明用户可完成相同流程，详见“测试缺口”。

## 阻塞问题

### P0：高风险待办只能查看，不能处理

**规格要求：**

- 退款必须关联原消费，关联后才影响统计；找不到原消费时停在待确认，不能默认作为收入（规格 2.1、5）。
- 提现到银行卡必须逐笔选择未追踪账户调拨、投资、现金消费或其他（规格 2.1、3.3）。
- 人际转账、红包、收款必须人工定性（规格 2.1、3.3）。

**证据：**

- `app/refunds/linking.py:64-166` 实现了 `link_refund_to_ledger()`：校验退款来源、待确认状态、原消费和退款额度，并以事务完成关联。
- `app/routers/inbox.py:61-75` 的 `GET /inbox` 仅加载高风险待办；唯一 POST 入口 `POST /inbox/confirm`（78-115）调用的是仅面向分类区的 `confirm_group()`。
- `app/decisions/confirm.py:25-35, 146-150` 显式禁止退款、提现、人际转账和其他中性资金流进入批量确认。
- `templates/inbox.html:7-34` 只用表格展示高风险项；没有退款候选、关联按钮、逐笔定性表单或提交路由。
- `app/main.py:24-28` 仅挂载概览、导入、待确认、流水和规则路由；仓库中无任何已挂载路由调用 `link_refund_to_ledger()`。

**影响：**

用户一旦导入真实账单，退款、提现和人际资金交易将永久留在待确认。退款无法回写原消费周期，概览无法得到实际净成本；提现和人际交易也无法在经过用户确认后进入正确账本。该问题直接阻断规格验收条件：

- “提现到银行卡、人际转账和退款不能未经用户确认污染收入或消费统计”。
- “跨期退款关联后，原消费周期和分类的统计反映实际净成本”。

目前虽然不会错误污染统计，但也无法完成工作队列，属于安全但不可用的半成品。

**解决方式：**

1. 为每条 `refund_pending` 待办提供候选原消费列表。候选应由 `find_refund_candidates()` 产生，页面显示日期、商户、原金额、已退款金额、剩余可退款额和匹配依据；用户选择一条后通过新的 `POST` 路由调用 `link_refund_to_ledger()`。
2. 为 `withdrawal`、`person_transfer` 和 `other_neutral` 提供逐笔处理表单。服务层应只接受规格允许的用途/类型，并在同一事务中创建账本记录、关闭待办、写审计事件、同步批次待确认数。
3. 高风险处理成功后重定向或重新渲染待确认页，并显示受影响笔数和结果；失败时展示业务错误，不能返回 HTTP 500。
4. 新增 HTTP 级测试，上传包含各类高风险交易的样本后，仅通过浏览器路由完成退款关联、提现定性和人际转账定性，断言待办关闭、账本/统计/批次计数/审计事件全部一致。

### P1：流水详情与人工编辑未形成可用界面

**规格要求：**

`/transactions` 应展示来源、规则命中证据、退款关联、人工改动和批次归属，并保留简易补账（规格 3.4）。

**证据：**

- `app/routers/transactions.py:155-185` 实现了 `POST /transactions/{entry_id}/edit`。
- `templates/transactions.html:100-124` 的每行只提供删除表单（115-118），没有链接或表单可提交至编辑端点，也没有详情入口。
- 该表只展示来源商户、平台状态和批次号（107-111），没有规则命中证据；退款仅显示金额（106），没有关联来源、关联时间或可追溯入口。
- `app/ledger_repo.py:429-444` 的更新只写 `manual_edited = 1`，没有创建规格要求的 `manual_edit` 审计事件。

**影响：**

用户无法从产品面修正已入账交易。即使通过非 UI 方式调用编辑路由，后续也不能从流水页追溯编辑原因或规则应用证据。批次撤销依赖 `manual_edited` 阻止删除，但用户无法正常触发这项保护。

**解决方式：**

1. 在流水表中新增“编辑”和“详情”入口；编辑表单提交到现有编辑路由，或将其改为明确的详情页表单。
2. 详情页查询并展示来源流水、所属批次、规则应用审计事件、退款关联明细和人工修改审计事件。
3. 在 `update_ledger_entry()` 的同一事务中写入 `manual_edit` 审计事件，记录变更前后关键字段或至少记录记录 ID、操作者动作和修改摘要。
4. 为编辑入口、详情渲染和审计事件增加 HTTP 测试；已关联退款记录编辑仍必须满足现有退款约束。

### P1：批次撤销未明确列出阻塞项

**规格要求：**

撤销批次时，编辑或关联过的记录必须作为阻塞项明确列出，不能静默删除（规格 3.6、8）。

**证据：**

- `app/revoke.py:84-141` 正确收集 `manual_edited`、`refund_linked` 和 `ledger_referenced` 阻塞项；结果通过 `RevokeResult.blocked` 返回（184-190）。
- `app/routers/imports.py:116-117` 丢弃了阻塞项详情，仅将 `blocked_count` 插入提示文本。
- `templates/imports.html:26-51` 未渲染任何阻塞记录、记录 ID、阻塞原因或后续处理说明。

**影响：**

用户只知道“有 N 项阻塞”，不知道是哪个流水、为何保留、应编辑还是解除关联，无法安全完成撤销决策。这不满足“明确列出”的验收要求。

**解决方式：**

1. 将 `RevokeResult.blocked` 传入模板上下文，不得只传计数。
2. 在批次页显示本次撤销结果区：阻塞对象类型、ID、原因、人类可读说明，以及跳转至流水详情或退款处理页的链接。
3. 明确部分撤销后的语义：批次已标记撤销，但阻塞流水及其来源仍保留；页面应展示保留数量，避免用户误以为全量删除。
4. 增加 HTTP 测试，构造人工编辑和退款关联阻塞项，验证页面包含对应记录与原因，而非仅有总数。

### P1：交付状态和用户运行文档与实际产品面不一致

**证据：**

- `docs/STATUS.md:34-36` 在审查开始时仍将阶段七列为“可进入”，没有阶段七报告或裁决。
- 根目录 `README.md:5-11, 34-54` 仍将 `/review`、`/cleanup` 和 `/export.csv` 描述为当前产品面；生产应用 `app/main.py:24-28` 未挂载这些路由，且测试 `tests/test_v2_routes.py:32-35` 断言 `/review` 与 `/cleanup` 返回 404。

**影响：**

用户会按 README 访问不存在的页面；维护者也无法从唯一状态页区分“阶段六准入通过”与“阶段七交付审查失败”，增加真实账单误导入和错误发布的风险。

**解决方式：**

1. 立即更新 `docs/STATUS.md`：阶段七标记为不通过，并链接本报告。
2. 立即更新 README 为当前实际挂载的页面和支持范围；不得保留未挂载路由作为当前功能说明。
3. 所有 P0/P1 修复和重新审查完成后，新建后续阶段七复审报告；再回写 `STATUS.md`，不得用口头“已完成”替代状态更新。

## 测试缺口与成因

### 直接调用内部服务导致“端到端”覆盖失真

`tests/test_e2e.py` 的退款和完整流程测试直接导入并调用 `link_refund_to_ledger()`：

- `tests/test_e2e.py:30` 导入领域服务。
- `tests/test_e2e.py:210, 248, 339` 直接执行退款关联，未经过任何 HTTP 路由或模板提交。

因此，这些测试证明退款服务层在给定参数时可用，但不证明用户能看见候选、选择原消费、提交关联或理解失败提示。提现和人际转账只被验证为“进入待确认”（173-185），未验证“用户可逐笔完成处理”。

**修复测试策略：**

- 服务层测试继续保留，用于验证事务、不变量和边界。
- 验收测试必须从真实上传请求开始，之后仅使用公开 HTTP 路由和 HTML 表单字段完成所有用户动作；验收测试不得直接调用只为 UI 提供能力的领域服务。
- 为每一条规格验收条件建立测试映射，至少标注“服务层”“HTTP/UI”“真实格式样本”三个层次；只有三者满足才允许标记为阶段七通过。

### 阶段门禁定义缺少“可操作性”检查

此前审查重点集中在导入原子性、退款约束、统计正确性、撤销保护和解析异常处理。这些工作质量较高，但阶段七没有以用户任务为单位复核“路由已挂载、模板有控件、操作可提交、结果可追溯”。

**修复交付门禁：**

发布前针对每个需求强制逐项确认：

1. 有受约束的服务层实现和事务边界。
2. 有已挂载的公开路由，不依赖测试或 REPL 直接调用。
3. 有可发现的页面入口、表单控件、成功反馈和失败反馈。
4. 有 HTTP/UI 验收测试覆盖成功、拒绝和数据一致性。
5. 有真实格式匿名样本或真实账单用户验收记录。
6. `docs/STATUS.md`、README 和阶段报告已同步更新。

任一项缺失，功能状态只能是“实现中”，不得标记为“阶段完成”或“可发布”。

## 根因判断

本次不通过的首要原因不是模型能力，也不是 PRD 缺乏明确性。

- **PRD 足够明确：**规格 2.1、3.3、3.4、3.6 和验收条件明确写出了退款关联、提现逐笔选择、人际转账人工定性、流水追溯和撤销阻塞项展示。
- **提示词可加强但不是根因：**若提示词仅要求“实现退款/待确认/撤销”，模型容易停在服务层；但规格已经提供了足够的产品行为约束。
- **首要根因是执行与验收断层：**将“存在领域服务”和“测试直接调用成功”错误等同于“用户可完成产品任务”。路由、模板、可操作 UI、HTTP 验收测试和交付文档未作为同一功能的完成条件。

建议后续任务指令明确写入以下不可协商要求：

> 后端服务不等于功能交付。每个用户需求必须提供已挂载路由、页面操作入口、成功/失败反馈和仅经 HTTP 完成的验收测试；测试不得用直接调用领域服务替代用户流程。

## 重新验收条件

只有同时满足以下条件，阶段七才可重新审查：

- P0 退款、提现、人际/其他资金流均可在 `/inbox` 逐笔完成，且错误不会污染统计或返回 500。
- 流水页可编辑并查看来源、批次、规则、退款和人工改动证据；编辑产生审计事件。
- 批次撤销页面逐项列出阻塞记录及原因。
- 新增的 HTTP/UI 端到端测试覆盖上述流程，且全量 `pytest` 通过。
- 使用用户确认的真实支付宝 CSV 和微信 XLSX 在本地完成一次受控导入、处理、统计核对和撤销演练；原始文件不落库。
- 本报告之后的复审报告、`docs/STATUS.md` 和 README 结论一致。

在此之前，允许继续开发和使用匿名样本验证；不建议向正式 `.data/ledger.sqlite` 导入真实财务账单。
